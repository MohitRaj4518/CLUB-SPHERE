Person 2: Client-Side Logic & Browser APIs

Vanilla JavaScript (ES6+)
Technologies Covered: JavaScript ES6+ URLSearchParams API DOM Manipulation Fetch API (async/await) FormData API RegExp Validation
  • Dynamic URL Routing: Uses the native URLSearchParams API to parse ?club=<id> and dynamically render all 5 distinct societies through a single template.
  • Modular DOM Card Generation: Programmatically constructs club banners, 4 specialized wings per society, numbered activity lists, and core team member cards.
  • Mutually-Exclusive Form Accordions: Event listeners ensure opening the "Register" accordion automatically collapses the "Withdraw" panel to prevent interface clutter.
  • Asynchronous Network Integration: Uses native fetch() with async/await to dispatch POST and DELETE payloads, giving instant visual feedback in .form-message.
Presentation Speaking Script (30 seconds): "I handled the Client-Side Logic using modern Vanilla JavaScript. Using the browser's URLSearchParams API, a single template dynamically renders all 5 college clubs. I used the native Fetch API with async/await to communicate with our server asynchronously. I also built the interactive form accordions that validate student inputs and handle both registration and self-service withdrawals in real time."
Probable Viva Question: How does the client validate inputs before sending them to the backend?
Answer: Two-layer validation: HTML5 pattern regex checks format on input, and JavaScript validates field presence before fetch() dispatches the payload.

Person 3: Backend Server & RESTful API Architecture

Node.js • Express.js 4
Technologies Covered: Node.js Runtime (v24) Express.js (v4.21) express.json() express.static() RESTful Routing Error Middleware
  • Server Initialization (server.js): Mounts static file serving for the frontend, JSON request parsing, and establishes the MongoDB connection before listening on port 5001.
  • RESTful API Design (routes/eventRegistrations.js):
    • POST /api/events/:eventId → Validates input against whitelists and saves registration.
    • DELETE /api/events/:eventId → Finds and deletes registration matching roll number and email.
    • GET /api/events/:eventId → Protected coordinator route returning attendee counts and roster.
    • GET /api/health → Operational heartbeat monitor returning status 200.
  • Global Error Handling Middleware: Intercepts malformed JSON payloads (SyntaxError) returning HTTP 400 Bad Request instead of allowing unhandled server crashes.
  • Whitelisting & Validation: Strictly enforces input parameters against 15 predefined campus event IDs across the 5 societies.
Presentation Speaking Script (30 seconds): "I am covering the Backend layer powered by Node.js and Express.js. Our server serves the static frontend assets and exposes clean RESTful API endpoints for event operations. I implemented JSON body parsing, input whitelisting for our 15 campus events, and global error middleware to ensure malformed requests never crash the server. The architecture strictly follows REST principles with standard HTTP status codes like 201 Created, 400 Bad Request, and 409 Conflict."
Probable Viva Question: Why did you choose Express.js for the routing layer?
Answer: Express provides minimalist, unopinionated routing, built-in static asset serving, and straightforward middleware chaining for JSON parsing and error management.

Person 4: Database Layer, Data Modeling & Security

MongoDB • Mongoose ODM • Security
Technologies Covered: MongoDB Community Server Mongoose ODM (v8.9) Compound Unique Indexes Data Normalization Regex Validation Header Auth (x-admin-key)
  • Document Schema (models/eventRegistration.js): Mongoose schema defining eventId, eventName, club, name, rollNumber, branch, year, email, and createdAt.
  • Compound Unique Indexing: { eventId: 1, rollNumber: 1 }. Mathematically guarantees a student can only register once per specific event, while freely participating across different club events.
  • Data Normalization: Auto-uppercases roll numbers (uppercase: true, trim: true) and lowercases emails to prevent case-sensitive duplicate registrations and withdrawal failures.
  • Security & Coordinator Access: Secures attendee lists with custom HTTP header authentication (x-admin-key), querying records via .lean() for optimal read performance.
  • Email Domain Verification: Strict server-side regex enforces official IIIT Kota email domain (/^[a-z0-9._%+-]+@iiitkota\.ac\.in$/).
Presentation Speaking Script (30 seconds): "I am presenting the Database and Security layer. We use MongoDB with Mongoose ODM to persist registrations. The standout engineering feature is our compound unique index on { eventId: 1, rollNumber: 1 }—this mathematically guarantees that a student cannot register twice for the same event while allowing multi-event participation. We normalize roll numbers to uppercase, enforce official @iiitkota.ac.in email regex validation, and secure the coordinator attendee roster with custom header authentication."
Probable Viva Question: How does MongoDB handle double-registration attempts?
Answer: When MongoDB detects a duplicate { eventId, rollNumber } key, it throws error code 11000, which our Express route intercepts to return an HTTP 409 Conflict.
